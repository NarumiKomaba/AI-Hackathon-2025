# 詳細設計書作成プロンプト

以下の条件を満たして、与えられたソースコード群を基に、完全かつ網羅的な詳細設計書を作成してください。
設計書は以下の章立て・構成に従い、システム全体の設計を正確かつ簡潔に記述することを目的とします。

---

## 1. 詳細設計書構成

### 表紙および目次
*   **表紙**: 
    *   システム名
    *   詳細設計書の作成日、バージョン、作成者名
*   **目次**: 各章のタイトルとページ番号を記載。

### 2. システム概要
*   **目的と背景**: システムの開発背景と目的を記述。
*   **全体像**: 
    *   システムの機能概要とスコープ。
    *   **ディレクトリ構成**: 主要なフォルダ・ファイルの構造をツリー形式で記述。
    *   **設計思想・選定理由**: アーキテクチャや技術スタックの選定理由、開発哲学（Design Philosophy）。
    *   ファイル間の依存関係を簡易図で示す（例：矢印やボックスを用いた図解）。

### 3. モジュール設計
この章では、システムを構成する各モジュールについて記述します。
*   **3.1 モジュール一覧**: 
    *   モジュール名とその役割を表形式で記述。
*   **3.2 モジュール詳細**: 
    各モジュールについて、以下を記述：
    *   概要：モジュールの役割と責任。
    *   **主要機能・クラス・メソッド**: 関数名、引数、戻り値、処理内容を具体的に記述。
    *   依存関係：他モジュールとの依存性とその影響。
*   **3.3 AI・LLM実装設計（Project Quest独自）**:
    *   **AIモデル設定**: 使用モデル、パラメータ設定（Temperature, Token limits）。
    *   **プロンプトエンジニアリング**: 
        *   **System Prompt**: キャラクター人格（PMO, 営業など）の定義内容。
        *   **Chain of Thought**: 思考プロセスを含めるか、Json Modeを強制するか等の戦略。
    *   **オーケストレーション**: 複数AI間の対話フロー制御ロジック（評議会機能など）。
*   **3.4 フロントエンド設計方針（Next.js App Router）**:
    *   **Rendering Strategy**: Server Components (RSC) と Client Components (CC) の分割指針。
    *   **Routing & Layouts**: ディレクトリ構成とLayoutのネスト構造。
    *   **State Management**: URL Search Params, Context, Local State の使い分け。

### 4. データ設計
*   **4.1 データ構造**: 
    *   使用される主要なデータ構造（リスト、辞書、クラスなど）の仕様を記述。
    *   クラス構造を簡易的なUML形式で記載：
      ```text
      +-------------------+
      | クラス名          |
      +-------------------+
      | - プロパティ      |
      | + メソッド()      |
      +-------------------+
      ```
*   **4.2 データベース設計（使用する場合）**: 
    *   ER図をテキストで表現： `[テーブルA] ――> [テーブルB]`
    *   各テーブルの定義（カラム名、データ型、制約）。

### 5. インターフェース設計
*   **5.1 内部インターフェース**: モジュール間のやり取り（関数やクラスの呼び出し方法）。
*   **5.2 外部インターフェース**: 外部システムやAPIとの接続仕様（リクエスト/レスポンス形式、エンドポイント等）。

### 6. 処理フロー
*   **6.1 システム全体のフロー**: システムの主要な処理フローをフローチャートやシーケンス図で記述。
*   **6.2 モジュール単位のフロー**: 各モジュール内の主要処理について詳細を記述。

### 7. 信頼性・運用監視設計
*   **7.1 例外処理・エラー設計**: 
    *   エラー条件：各モジュールで発生しうるエラー条件。
    *   例外処理フロー：エラー発生時の復旧や通知のフロー。
*   **7.2 ログ設計**: ログ出力方針、レベル（DEBUG, INFO, ERROR等）の使い分け、フォーマット、出力先。
*   **7.3 監視方針**: システムの死活監視やパフォーマンス監視の考え方。

### 8. インフラ・セキュリティ設計
*   **8.1 実行環境**: 必要な言語バージョン、OS要件、依存ライブラリ一覧。
*   **8.2 設定ファイル・環境変数**: 環境変数（.env）や設定ファイルのパラメータ定義と役割。
*   **8.3 セキュリティ設計**: 認証・認可、機密情報保持、通信の暗号化などの方針。

### 9. テスト・デプロイ設計
*   **9.1 テスト計画**: 単体テスト、結合テストの設計（入力、出力、期待結果）。
*   **9.2 デプロイフロー**: ビルド手順、CI/CDのフロー、リリース手順。

### 10. 設計上の課題と今後の検討事項
*   現時点での設計の課題、実装・運用段階で想定される問題点とその対応案。

---

## 出力形式
*   設計書は **Markdown形式** で記述。
*   図解には Mermaid 記法や簡易テキスト図形を使用。
*   必要に応じて、箇条書きやリストを活用して可読性を高めること。

---

## 注意事項
*   **依存関係の正確な把握**: ソースコード内で明示的・暗黙的に表現されている依存関係を正確に分析。
*   **曖昧な仕様の対応**: 設計に不足する情報があれば仮定を明示し、それを注釈として記述。
*   **一貫性の確保**: 全章にわたって整合性を保ち、重複や矛盾を避ける。
